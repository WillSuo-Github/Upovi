# In-application Mac App Store updates, 0.4.8

Upovi can check compatible native Mac App Store installations and initiate their updates from its own detail/review/batch views. Opening the App Store window is no longer the normal action for supported Store apps. Download and purchase entitlement handling still belongs to Apple's Store services and requires the appropriate Apple Account to be signed in. Native account or administrator authentication may appear. Upovi does not request or store Apple Account passwords, acquire new apps, make purchases or bypass Store ownership.

## Checks and UI

The bundled checksum-pinned mas 7.0.0 executable is invoked directly, without its shell wrapper, Homebrew or jq. Minimal structured installed-app records are read from Spotlight and matched by bundle ID and filesystem identity (including the APFS Data-volume alias). A single coalesced snapshot obtains public catalog versions for confirmed Store IDs. Unrecognized IDs, unavailable products, incompatible OS requirements, iOS-only releases, duplicate installations and failed checks are not silently reported current. TestFlight or missing-ID installations remain unconfirmed/manual. Public Store version metadata can lag behind the actual Store and does not establish ownership or detect every build-only update.

Source-confirmed newer Store versions participate in update counts, skip/snooze, notifications and Update all. An already checked supported Store installation also offers Check and update this application. This explicit action lets the Store's download metadata decide whether an update is needed, including when public metadata is delayed. Its confirmation may show the same marketing version on both sides; that is a check-and-update request, not a claimed newer release. A successful unchanged result has its own current state and is not recorded as an installed upgrade. Unfinished batches still require a fresh source check and confirmation after relaunch.

The shared batch review clearly explains that Store updates have no Upovi retained-copy rollback or byte-range cache/pause controls. Store services do not always expose detailed download progress, so Upovi reports an indeterminate Store-operation stage where necessary. Stop-after-current does not promise to cancel a Store operation that has already been handed to Apple. A timed-out/failed operation is unconfirmed, and the system service may still finish; explicit retries recheck the installed state.

## Protected execution

A dedicated signed UpoviStoreInstaller and signed embedded Store bridge are copied into a new root-owned private staging directory and their pinned identifiers/Upovi signing team are verified before execution. The bounded selected plan permits only an existing signed Store app directly under /Applications, a numeric Store ID, a current-or-newer selected version and the active graphical user. No persistent root daemon or sudoers changes are made.

The protected helper shares the existing installation lock, creates a root-owned Store transaction journal, verifies that the original bundle/version/developer/receipt still match, refuses a running app, rechecks a unique Spotlight ID/path mapping, and independently checks the Store product's bundle ID and Mac/OS compatibility. Only the update command for that exact installed ID can run in the graphical user's bootstrap session. It uses a minimal environment and never invokes get/install/purchase/uninstall. Success requires observing a valid matching signed Store installation at the original path with the selected version or later. Store journals and bounded logs remain private; diagnostics do not export Store raw output or account data. Recovery/cleanup controls for direct-distribution backups do not apply to Store transactions.

mas uses Apple's private Store frameworks. Compatibility and authentication behavior are OS/account-specific; this is an experimental integration rather than a public Apple management API. [Upstream documentation](https://github.com/mas-cli/mas/blob/v7.0.0/README.md) describes Store/account requirements and unsupported cases. Bundled and transitive dependency notices are retained in Vendor and the distribution Resources directory.

## Acceptance

173 local tests passed (156 core, 17 application-store workflow tests), including Store metadata identity/OS/platform failures, snapshot reuse and invalidation, zero-ID handling, Unicode JSON record boundaries, denied input plans, current-versus-installed results, batch history and review routing. Actual read-only checks on this host recognized 23 receipt installations: 21 matched a compatible public Store product and were current; two had no confirmed Store ID and stayed manual. This does not establish download/installation success.

The Developer ID signed universal candidate includes both signed helpers and the checksum-pinned universal bridge. The bridge launches and reports version 7.0.0. The owner explicitly selected Shazam for a real check-and-update operation. Native production views displayed its Store identity, the one-application review and Store-specific limitations. Starting that review ran the protected helper and Apple Store accurate check, returning a verified current result: Shazam remained 2.11.0 (821), one completed item and zero failures. No newer release was installed, so this does not validate an old-to-new Store download/replacement. Other daily applications were excluded. The same authorized Shazam operation was repeated on the final clean-source signed universal artifact after native owner authentication; it again returned current, and closing the result preserved the exact Store-current detail. All three macOS CI jobs passed. Earlier dirty-source candidate execution and final artifact identity are tracked separately in [version-specific evidence](evidence/0.4.8-app-store-updates.json).
