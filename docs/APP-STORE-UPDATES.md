# In-application Mac App Store updates

Upovi can check compatible native Mac App Store installations and initiate their updates from its own detail/review/batch views. Opening the App Store window is no longer the normal action for supported Store apps. Download and purchase entitlement handling still belongs to Apple's Store services and requires the appropriate Apple Account to be signed in. Native account or administrator authentication may appear. Upovi does not request or store Apple Account passwords, acquire new apps, make purchases or bypass Store ownership.

## Checks and UI

The bundled checksum-pinned mas 7.0.0 executable performs Store inventory, update detection, product lookup, download and installation. It is invoked directly, without its shell wrapper, Homebrew or jq. A single coalesced snapshot uses `mas list`, `mas lookup <IDs>` and `mas outdated --inaccurate --check-min-os <IDs>`. Upovi matches bundle IDs and filesystem identities (including the APFS Data-volume alias), validates exact Mac products and OS compatibility, and accepts only matching update versions reported by mas. Duplicate, stale or mismatched results never authorize installation. A failed detection is not reported current, even when a catalog lookup succeeds.

Upovi no longer calls AppStoreDaemon or CommerceKit itself to refresh or read native update lists. The former native status helper and its 505 gating are removed in local build `202611040007`. mas still uses Apple's private frameworks internally for downloads and installation. Upovi also no longer performs a separate regional HTTP catalog lookup: products unavailable through mas remain unconfirmed, with an App Store confirmation message. TestFlight or missing-ID installations remain manual; known discontinued Store products retain their developer migration guidance.

Ordinary mas detection uses public catalog metadata. A candidate is not proof of ownership or an account-specific update offer, and metadata can lag or miss build-only releases. Apple decides actual availability and account eligibility when an update is submitted. Background checks never use `outdated --accurate`, which starts and cancels downloads and can show authentication dialogs or encounter rate limits. The earlier signed 505 rejection is preserved as historical evidence in [automatic updates and channels](AUTOMATIC-UPDATES-AND-CHANNELS.md).

An already checked supported Store installation still offers Check and update this application, without querying a native update cache. This explicit action rechecks the product through mas. If its public version is unchanged, no download is started; it does not guarantee discovery of build-only releases. Its confirmation may show the same marketing version on both sides; that is a check-and-update request, not a claimed newer release. A successful unchanged result has its own current state and is not recorded as an installed upgrade. Unfinished batches still require a fresh source check and confirmation after relaunch. Background detection never uses mas's download-and-cancel accurate probe.

The shared batch review clearly explains that Store updates have no Upovi retained-copy rollback or byte-range cache/pause controls. Store services do not always expose detailed download progress, so Upovi reports an indeterminate Store-operation stage where necessary. Stop-after-current does not promise to cancel a Store operation that has already been handed to Apple. A timed-out/failed operation is unconfirmed, and the system service may still finish; explicit retries recheck the installed state.

## Protected execution

A dedicated signed UpoviStoreInstaller and signed embedded Store bridge are copied into a new root-owned private staging directory and their pinned identifiers/Upovi signing team are verified before execution. The bounded selected plan permits only an existing signed Store app directly under /Applications, a numeric Store ID, a current-or-newer selected version and the active graphical user. No persistent root daemon or sudoers changes are made.

The protected helper shares the existing installation lock, creates a root-owned Store transaction journal, verifies that the original bundle/version/developer/receipt still match, refuses a running app, rechecks a unique Spotlight ID/path mapping, and independently checks the Store product's bundle ID and Mac/OS compatibility. Only the update command for that exact installed ID can run in the graphical user's bootstrap session. It uses a minimal environment and never invokes get/install/purchase/uninstall. Success requires observing a valid matching signed Store installation at the original path with the selected version or later. Store journals and bounded logs remain private; diagnostics do not export Store raw output or account data. Recovery/cleanup controls for direct-distribution backups do not apply to Store transactions.

mas uses Apple's private Store frameworks. Compatibility and authentication behavior are OS/account-specific; this is an experimental integration rather than a public Apple management API. [Upstream documentation](https://github.com/mas-cli/mas/blob/v7.0.0/README.md) describes Store/account requirements and unsupported cases. Bundled and transitive dependency notices are retained in Vendor and the distribution Resources directory.

## Local build 202611040007 acceptance

The owner authorized a real update of AdBlock Pro only. A Developer ID signed native acceptance harness compiled from the current production views and services, using the current signed helpers and bundled mas, displayed the one-app review and completed the upgrade from `13.0.0 (349)` to `13.1.0 (350)`. The installer returned `installed` without a failure, the native UI showed one completed item, deep/strict/all-architecture signature validation passed, Gatekeeper accepted the app as Mac App Store software, and its Store receipt remained present. A fresh mas source check then returned current with zero candidates.

This validates an actual old-to-new download/install through the current source, not a released artifact or Safari extension behavior. No other app was selected and the installed Upovi was not replaced. Temporary acceptance processes and bundles were removed after recording [upgrade evidence](evidence/adblock-store-upgrade-202611040007.json).
