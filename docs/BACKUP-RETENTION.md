# Application backup storage and retention

Ordinary completed application backups are ZIP archives under `~/Library/Application Support/Upovi/Installations/Backups.noindex`. They are not executable application bundles and are not registered as installed applications. Each archive is extracted and its recorded identity and signature verified before its checksum is written into the installation journal. The archive and journal are synchronized before removing the runnable source. Restoring checks the recorded archive path, checksum, bundle identity, version and developer before replacing the original application path.

In-flight rename operations stay on the destination volume in a private `.upovi-recovery-<uid>.noindex/<transaction-id>` directory with an indexing-exclusion marker. Completed legacy `.upovi-backup-*.app` and `.upovi-replaced-*.app` copies are migrated to archives, and their exact LaunchServices registrations (including nested helpers) are removed. A migration interrupted after journal publication can safely resume. Recovery uses a separate extraction entry point that preserves app-contained relative framework links, rejects links escaping the application root and never writes through a symlink. Download extraction retains its previous stricter link policy.

The ordinary retention policy keeps the latest completed backup per application for at most seven days. A restored installation starts a fresh seven-day interval for its displaced newer copy. A newer correctly signed installed version permits deletion of an older completed backup without granting permission to roll it back. Expiration permanently removes retained data; installation journal metadata remains. The History & Recovery page describes this policy. Startup, hourly idle maintenance and completed batches apply it without downloading or installing anything.

Prepared, backed-up, failed and interrupted transactions are never automatically deleted. A missing, changed or unverified live application also prevents automatic expiration: a matching signed completed backup can still be migrated to an inert archive, preserving the only remaining recovery copy. A running backup is left alone. Unknown locations, linked storage, changed archives and signature failures preserve recovery material and produce bounded diagnostics. Recovery authority is revoked durably before automatic deletion; interrupted cleanup can resume. A journal lock permits parallel application installations while excluding maintenance across processes. Isolated application configurations disable automatic maintenance by default.

Protected administrator backups remain in their root-owned transaction directories, with an indexing-exclusion marker. The same latest-copy/seven-day expiration rule runs opportunistically inside an already authorized administrator operation. It does not start a new background authorization prompt. The explicitly requested transaction is excluded, so selecting Restore or Inspect cannot expire that same backup. Incomplete and pending-finalization transactions remain protected. Returned transaction IDs update the host's cached cleanup state.
