# App Management access guidance

Upovi offers a skippable first-launch guide, also available in Settings and after a batch encounters an application write-access failure. Existing installations see the introduction once. Skipping does not disable scanning or update checks. The guide shows separate component availability and actual write-verification status, with per-application success checks and actionable failures.

**Open Settings** goes directly to System Settings → Privacy & Security → App Management. The user should review both Upovi and **Upovi Installer**, which some systems display as **UpoviStoreInstaller**. **Show Installer** reveals the embedded helper in Finder if it needs to be added with “+”. The helper is not executed by the Finder action. Opening Settings invalidates previous verification evidence; it never records consent as granted or retries an installation.

**Verify Access** is an explicit user action. It requests administrator authorization once for the selected blocked Store applications (or one installed Store application if there are no blocked targets), and uses the same signed, protected helper launch path as Store updates. Each typed plan is marked as an access probe. The helper validates the current signed application, creates and removes an empty uniquely named file in its receipt directory, then returns `accessVerified` before any product lookup, download, installation or purchase-receipt repair. Cancellation or an incomplete response cannot produce success. Results apply only to the targets and time tested, not to every system privacy permission. The response parser accepts LF, CR and CRLF because AppleScript converts shell newlines to carriage returns. After successful verification, Done closes the guide and the Updates reminder changes to Access Verified with an explicit recheck action.

The privileged launch registers the exact temporary signed installer bundle in the active console user's LaunchServices registry before execution, then unregisters it before removing the protected temporary directory. This addresses a real failure observed on the reporting Mac: App Management switches for Upovi and UpoviStoreInstaller were both enabled, but the permission service returned `failed to get bundle URL` during the pre-download write probe. Registering the actual temporary bundle made the same probe succeed for Developer and AdBlock Pro without changing privacy switches. The structured failure now preserves the underlying allowlisted domain and numeric code; a generic write denial no longer tells the user that they necessarily forgot to grant permission.

Permission failures retain blocked application references and correlated `permissionDenied` diagnostic entries. A batch presents one guide after its jobs finish and keeps a reminder after dismissal or restart. Successful permission verification does not mark a failed update as completed. **Recheck Blocked Apps** still refreshes only the latest failed Store items and returns to the update confirmation page. Returning from Settings, reopening Upovi or completing a permission probe never installs an update. Only an explicit update confirmation can start another attempt.

Upovi does not query private TCC APIs or read/modify the TCC database to display permission status. The main application and Store installer contain Apple's [NSAppBundlesUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsappbundlesusagedescription) purpose text. The manual navigation path remains visible because settings links can vary by macOS version.

The original build `202611140002` [publication](https://github.com/WillSuo-Github/Upovi/releases/tag/build-202611140002) and [pre-publication acceptance](evidence/app-management-202611140002.json) predate this revised flow. Build `202611140003` validation is recorded separately in [local evidence](evidence/backup-and-access-202611140003.json). Real privacy switches remain unchanged; Store applications were probed, not updated, during this acceptance.
